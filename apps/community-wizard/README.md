# Community wizard v1

## Current delivery contract, 2026-11-14

The browser uses Solid and `@solidjs/web` 2.0.0-rc.21, with the matching signals
and compiler, `@solidjs/vite-plugin` 3.0.0-next.57 and Vite 8.3.6. Its independent
manifest and lockfile pin this cohort explicitly. Keep those packages aligned
when updating the runtime, and run both the package check and browser journey.

The Wizard's v1 target is one fresh supported Linux installation with browser
setup, a real ordinary HTTPS community, automatic community registration,
member authentication, optional eligible names, first-song publication/playback
and persistence through an ordinary restart. HNS verification may continue
separately while the Web2 community is usable. No manual Pirate approval step
belongs in this flow.

This README specifies that target; it is not a deployment or readiness report.
The current create-only profile is a proof-qualified source milestone and cannot
yet represent the required pending-HNS community. That gap must be implemented
through the explicit versioned joins below, not by removing authority checks.
No fresh genuine host target/readiness or runtime acceptance is established here.

The ordered requirements, state meanings, pending profile proposal and exact
ownership are in [the onboarding specification](../../docs/v1-onboarding-linux-wizard.md).
It takes precedence over the older setup-page, per-TLD registry, operator-funded
and provider-account onboarding instructions in this file's history.

## What the operator should experience

1. Start the actual packaged helper on the documented supported Linux server.
   On a VPS, keep the server terminal and operator-computer browser distinct.
   The authenticated bootstrap prints the real SSH forwarding command and
   matching loopback URL after it is listening. The setup listener stays private.
2. Choose an actually supported provider-assigned HTTPS address or custom Web2
   hostname. Prove the selected account/resource or exact hostname control.
   Do not infer full-app control from a workers.dev setup page or HTTP 200.
3. Review the neutral community title, canonical HTTPS origin, full application,
   persistent services, selected shared profiles and actual costs. Generate
   technical IDs; retain the portable community key, installation mapping and
   original resources. Provision only through the real selected backend.
4. Follow the generated DNS/routing instructions and current checks. Show each
   actual record type/name/value/TTL/proxy setting where applicable, with copy
   controls. Verify real TLS and a fresh installation-bound nonce/readback from
   the full app, including the selected authentication/media/jobs interfaces.
5. After actual checks, automatically register/reconcile the same neutral HTTPS
   community through the scoped registrar and verify its canonical readback.
   Report appReady from real evidence and offer Open actual site at that origin.
   Display website, registration and namespace status separately.
6. Authenticate, publish/play the first song, and verify an ordinary restart.
   A lost reply or uncertain operation reopens its original status; it never
   silently starts another transaction, mint or deployment.

Until genuine verification, the Wizard omits the requested TLD from public
community profiles, titles, ownership badges, namespace usernames and verified
namespace discovery; saving preparation intent reserves nothing. Private
preparation state does not guarantee confidentiality: DNS/HNS publication and
external observations may reveal the requested TLD before verification. Pending
public identity is a human title and the provisioned HTTPS address. An SLD hosting
address never confers parent or sibling issuance rights. App and installation
identity do not derive from the requested TLD.

Membership and community use do not require a name. When actual namespace and
member authorization are ready, eligible 8+ names have zero name price under the
selected rules. Pirate funds eligible operations with finite policy/gas bounds.
There is no operator funding-wallet or ACRCloud account setup step and no paid
name fallback. Show real term/expiry/renewal and any unrelated hosting/storage
charges; neither a budget proposal nor a saved secret proves enforcement.

## Credentials and selected infrastructure

Use established Alchemy/Infisical managed authentication and scoped secret
references. Alchemy is the sole reconciler of its Cloudflare resources. Use cf
only for the supported authentication/diagnostic path; do not add Wrangler or a
second secret synchronizer. Publication/recognition use the selected shared
service, without asking community operators for its provider or treasury keys.
Only genuinely selected features request their own necessary access.

Keep secrets and signing keys out of command arguments, browser responses,
setup JSON, source and public logs. Account-wide credentials remain privileged
even when an adapter selects one folder or resource prefix. Verify exact current
account/scope and secret persistence through the owning workflow. Saved access,
verified services and whole-app readiness are different states. Missing managed
inputs require an actionable unavailable state, never borrowed keys or fake health.

The trusted runner retains private permissions, encrypted state/diagnostics where
implemented, bounded outputs, exclusive custody and Host/Origin/CSRF/pairing
checks. Do not clear state or remove locks to escape unknown effects or a
decryption failure. Routine restart retains original keys/resources and reconciles
the same operation. Document every persistent directory and recovery limitation.

## HNS is a separate bounded job

Use the existing HNS ceremony service and its exact signed wire through a thin
same-origin adapter. Do not create a second service or let a browser select
remote endpoints or signers. Display real deadlines, retryAt and observations;
GET reads stored progress. Actual observations are scheduled or explicitly
requested, with finite attempts, delays, concurrency and job expiry.

ReadyToSubmit means preparation is ready, not verified namespace authority,
completed admission or permission to mint. The current service's unavailable
capabilities remain unavailable. Pending or expired preparation does not take a
healthy Web2 app offline. Expiry closes the job and requires explicit supported
restart/re-observation; it does not delete community/audit state or discard an
unknown transaction, journal or gas reservation.

Only genuine fresh proof and the actual admission/receipt/source checks enable
verified namespace attachment and short grants. Verification lapse or namespace
loss pauses relevant issuance/verified listing without NFT burn, seizure, loss
of locked renewal terms or automatic reassociation. Native HNS-browser access
is not a v1 gate. Spaces remains deferred.

## Source gaps and explicit version selection

Current V2 and create-only profile/3 still require a verified namespace proof
before prepare/apply. Directory/configuration and signed profile/current-authority
readbacks cannot yet represent the required pending HTTPS community. Core/W6/
Storage must accept and implement a new explicit pending profile and scoped
automatic registration, plus a later verified attachment operation. The public
pending record contains no requested TLD or fabricated proof. Keep the original
community key, installation mapping/resources, signed history and source pins.

The operational origin is currently immutable. Namespace attachment cannot
silently add an origin, change cookie/CSRF/MOSS audiences or alter Learning
consent. Multi-origin or Learning-consent changes need a separate reviewed
successor. Registry56's P0 scope-validity repair remains separately owned and
cannot be replaced by Wizard copy or a valid grant alone.

The Wizard owner supplies the UI/codec/ceremony adapter; Storage supplies actual
bootstrap/host/full-app and credential/readback producers; HNS/Naming supply
genuine ceremony/proof/current rights; core/Directory supplies the pending record,
scoped registrar and attachment/reader/cache contract. Member API/UI and funded
submission remain with their application/service owners. This documentation
does not activate any missing interface, provider, key, contract or funded action.

## Development and acceptance evidence

The existing source-checkout commands below are developer tooling, not the
packaged operator bootstrap or proof of a Linux full-app installation:

```sh
npm ci
npm run check
npm start
```

Run them only in their owning package under the assigned execution scope. None
of these commands was executed for this documentation proposal. The historical scaffold
provisions a setup-page recipe; its URL and success state cannot qualify
the required full application. The real installed Linux command/address must
come from its qualified package. Do not invent an entrypoint or reuse an old
preview as current acceptance.

Required owning checks remain honest. The revised flow needs actual browser
setup, account/resource and DNS/TLS control, nonce-bound full-app readback,
automatic registration, real member/name authorization, first-song playback and
ordinary restart/retry evidence on the selected host. Controlled fixtures, source
review and old setup-page receipts do not establish these results. Runtime
acceptance of the revised flow remains UNRUN; no ETA is promised.
