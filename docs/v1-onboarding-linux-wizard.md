# Linux community setup source

This browser flow creates, imports or restores the complete application on a
user-owned Linux server, including an existing VPS. The target called
local-linux means the server running the setup helper, not necessarily the
computer running the browser. The inspected description and fingerprint
identify that server. A different target uses its managed SSH connection.

For a VPS-hosted helper, the browser runs on the operator's computer through
the bootstrap's authenticated SSH tunnel. The bootstrap owner must print one
copyable forward command and its matching loopback URL, and distinguish that
temporary setup tunnel from the deployed app's independent public HTTPS origin.
The current HTTP Host guard requires the forwarded local port to match the
helper's bound port; the bootstrap must preserve that binding rather than
publishing the setup listener or disabling the guard. No command or active
bootstrap capability is manufactured by this source packet.

This flow does not select a VPS vendor. A setup-page deployment is a separate,
explicit Advanced Cloudflare recipe and is not a full Linux installation.

The Linux runtime owner must supply real target, credentials, encrypted backup,
complete-profile lifecycle, durable jobs, authority and independent receipt
readback services. The factory/type declarations alone implement none of them.
An unmounted runner reports Linux backend unavailable and cannot manufacture a
deployed state from credentials, settings, an outcome string or a capability flag.

## Browser flow

Choose the action and host first. Create asks for a community name, application
HTTPS origin and controlled TLD, selected service profiles, limits and storage.
The name supplies an editable identifier under Advanced. Import and restore
begin with the destination only; metadata and original identity come from the
inspected installation or authenticated backup. Technical contract, issuer,
migration and resource IDs are discovered in the resolved profile under Advanced.

Unsaved changes block inspection, verification, review and apply. The saved host
is displayed. Feature dependencies and missing backend support are explicit.
Learning includes its operator in the same application plan, using verified
service profiles and bounded speech/provider/activation limits. Saved managed
credentials remain distinct from verified services and application health.
Platform login and signing credentials are not accepted as community speech keys.

Public media uses Filebase IPFS. Private persistent data stays in a private host
volume. Recovery backups are encrypted before their transport to the selected
backup storage role. Filebase private objects are the default when discovered;
Backblaze B2 and custom S3 remain optional Advanced transports. Saved endpoints
do not prove access, encryption or restore compatibility.

Hosting an HTTPS application does not import a TLD. The required naming port
returns an explicit controlled-TLD or permitted-SLD proof with reserved
exclusions, including kaya.pirate. Review and apply revalidate current rights;
the actual operator must fence effects with another current authority check.
A stored proof or a hosting-origin string is never issuance authority.
Namespace-free bootstrap is not a supported alternative in this flow.

Restore uploads supported ciphertext and then asks for its separate recovery
key. The server checks the consumed ciphertext digest against the owning
store's immutable upload receipt. An interrupted/lost upload retains its
request identity; resume resends the same complete file, without byte-range
resume. Size and an indeterminate upload status are displayed. Streaming has a
separate bounded deadline from short metadata calls, with HTTP idle/header and
absolute limits. The backend must publish its real maximum supported size.

The backup owner must authenticate the complete consistent cohort, compatibility,
identity, secrets/session/revocation data and permitted recovery policies.
The browser defaults to revoking existing sessions when that actual policy is
supported; preservation requires explicit selection and verified implementation.
The key is cleared from the form after submission and is not journaled.
Restore cannot proceed when any required backend capability is missing.

## Operation identity and recovery

The private journal captures the complete plan, original resource identity and
operation before launch, then fsyncs the exact native deploy/restore intent.
Read-only reconciliation uses the original target and retained intent.
A lost HTTP acknowledgement returns the existing operation without another send.
Concurrent approvals CAS to a single operation. Source/artifact, full profile,
original resources, scope, backup cohort and policy remain bound to that intent.

Process custody and external effects are distinct. Uncertain custody retains
the active claim. Once actual process custody is cleared, settings and review
can be corrected while unknown effects still block apply. A reconciled failure
permits a reviewed descendant plan on retained identities. It never resets the
original intent, resource names or receipt history. Restart reconciles the
original operation; it does not rerun it. Identical readback results deduplicate,
and stale observations cannot replace a newer terminal state.

Terminal success requires the real owner to verify restricted receipts,
postguard/cleanup, every captured resource, full application/login/media and
selected Learning health. Restore additionally binds exact cohort and session
policy. Empty process lists, elapsed time or an incomplete foundation cannot
clear custody or qualify the application.

Journal records are atomically fsynced in an owned private directory. The
bootstrap supplies an actual exclusive custody lease and authenticated operator
session or paired SSH-forwarded channel. Loopback and CSRF are insufficient.
Origin/Host/CSRF checks remain required. No private state belongs in Git.
The bounded journal preserves distinct evidence; exhaustion blocks new work
and requires an owning-backend export/recovery path, not silent history pruning.
A real durable backend job driver is still required for lifecycle continuation
after browser/server interruption; this server journal alone is not that driver.

## Integration and evidence limits

The wizard consumes LinuxDeploymentPort v1 and NamespaceAuthorityPort from
server/linux-contracts.ts. The native LinuxOperatorAdapter types are imported
from their planned deploy/linux/operator-adapter-contract.ts owning path.
No runtime imports another worktree or the control plane. The Linux owner
supplies createLinuxDeploymentPort and all required services; bootstrap passes
them, naming, exclusive custody and authentication to createLinuxWizardRuntime.
That required construction is not wired by a default fake backend.

The port uses raw lowercase SHA-256 for canonical plan/profile digests and
native EvidenceRef hashes. Runtime source/artifact, ciphertext, cohort and
namespace evidence digest fields use 0x-prefixed SHA-256. The exact native
operator contract remains owned by the Linux runtime lane.
The separately proposed factory integration delegates canonical plan validation
to planFrom and preserves explicit retained upgrade actions.

The UI compares established standalone wizard and centralized Solid/Storybook
source. It retains the standalone wizard fields/cards and request-state pattern,
with no centralized auth, API or persona runtime. Additional host/authority,
full-profile and recovery steps reflect actual self-hosting boundaries.
No browser or visual parity acceptance follows from source inspection.

All new tests are prepared source, unrun. The controlled fixture is explicitly
not Linux, SSH, encryption, naming authority, real custody or provider acceptance.
The browser cases require a real built wizard but still use controlled adapters.
Required acceptance remains: real bootstrap to browser create/import/restore;
working MOSS login, media and selected Learning; persistence and restart;
interrupted jobs and upgrade reconciliation; and authenticated encrypted restore
on a second host under the explicit session policy. Fresh-account,
second-community, provider and device acceptance remain open.
