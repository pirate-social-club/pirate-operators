# Proposed bounded pilot architecture

Operator-owned community Worker -> authenticated HTTPS -> Pirate-owned gateway -> one authoritative sponsor-budget Durable Object -> separately isolated signing services -> chain. Reconciler, usage projection and alerting read the authoritative journal. No central sponsor secret is installed in a community account. Same-account private bindings can connect Pirate services; cross-account community requests require independent authentication.

Alchemy owns future resource provisioning. Infisical owns secret delivery per service scope. This packet provisions neither. Existing community Workers/D1/R2/jobs stay unchanged. The public gateway is stateless and performs bounded decoding and authentication; essential state is durable.

## One reservation transaction

For the small manually admitted pilot, one SQLite Durable Object coordinates the fixed chain's whole fee budget. It contains global, community and per-user counters, policy/admission revisions, the original-operation journal and final-intent reservations. Every reservation checks and changes all relevant rows in ONE synchronous storage.transactionSync callback: no await, external RPC, signature request or service call in that callback. Await durable storage completion before any external effect. Failure prevents signing.

Cloudflare's synchronous transaction and storage.sync facilities support this boundary; PITR can restore older storage. This proposal deliberately uses explicit transactions rather than relying on implicit batching. [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/), retrieved 2026-11-14.

A single bounded coordination object is a pilot tradeoff, not a production throughput claim. Ordinary application traffic and expensive RPC verification stay outside it. Sharding later needs reviewed escrow allocation: separate community objects and a global object do not form an atomic transaction. Global-first compensation alone is insufficient unless uncertain failures retain reservations and recovery is proven. No such distributed scheme is introduced here. [DO coordination guidance](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/), retrieved 2026-11-14.

Transaction predicates: active policy epoch, matching prior ledger revision, community admitted/not paused, exact supported route and operation, verified authorization digest, unused logical-operation identity, unused final intent, unexpired quote, available global/community fee headroom and user rate allowance. Atomically reserve worst-case native fee liability, mark both identities, allocate journal sequence, advance counters and append an event. Duplicate equal requests return the same reservation; altered duplicates conflict. No count-only budget or implicit unlimited default.

Rolling/global policy windows are not selected here. Any future reset must retain outstanding liabilities from prior windows. A new policy or epoch is not permission to discard unknown spends.

## Immutable identity and signing

Canonicalize a closed envelope and own its bytes before awaits. Bind communityKey/communityId, directory instance, installId, origin, namespace, chain, source profile, exact contract/code, actor, role, function and all arguments/value, logical operation, revisions, nonce and expiry. Reject unknown fields and alternate encodings. Digest generation and validators need later implementation and tests; the proposed TypeScript is not a validator.

Wallet requests carry a separately verified authorization challenge for the exact operation and domain, with nonce and expiry. This is required even if a merchant callback receives an unsigned intent. Service-originated requests use an authenticated service principal plus independently verified entitlement. Host/Origin, a claimed wallet, a community header or an operator app session is not enough. Check the manually maintained Pirate pilot admission and the existing authorization appropriate to the action; bind the installation as well as community. A new general membership database is not required. See READINESS.md for the per-action evidence and the first-claim/first-learning-authorization exceptions.

Validate every batch call and secondary effect: pre-calls, transfers, delegation/key authorizations, funders/settlers, fee token, payment recipient, account implementation and all domains. Default deny unknown structures, chain, value or selectors. Allowlisted target alone is insufficient. Explicit MOSS mode is a client preference; server enforcement is mandatory.

The final MOSS intent may change payer/fee fields from its initial request. Construct and validate those final bytes before reserving their final digest, while retaining the logical operation. The merchant documentation exposes a server policy callback and per-intent fee cap, but its permissive default must never be used. These hooks do not establish compatibility with this durable boundary: verify actual package sequencing before use. [MOSS merchant API](https://moss.megaeth.com/developers/packages/wallet-merchant), retrieved 2026-11-14.

Before reservation, Pirate's gateway independently reads the relevant state at a canonical safe block and simulates the exact action/account execution against that state. Bind the simulation, permission evidence and validity window to the owned call digest. A known revert or unavailable required state prevents reservation. Simulation does not guarantee inclusion-time success: revalidate after waits, limit concurrent requests and charge actual reverts against both fee budgets and per-wallet abuse controls. The merchant package's lack of a required RPC endpoint does not supply these checks or prevent Pirate from performing them.

Journal sequence: validated -> reserved -> signing-intent-durable -> signed-original-durable -> send-intent-durable -> submitted-or-unknown -> canonical-safe-success/revert. External signer calls are idempotent against exact bytes and reservation identity. Persist signer-side exact request/result before reply. A lost signing response is uncertain authorization, not permission to refund and mint a new request. Recheck pause, epoch, expiry and authority after external awaits before the next effect.

For backend transactions persist exact signed raw bytes and hash, sender, nonce, chain and deployment before broadcast. For MOSS persist exact final intent/digest, payer authorization, account nonce/expiry and eventual execution transaction. An outer relayer hash alone does not prove the intended payment or execution.

## Reconciliation and paused recovery

Unknown transaction/receipt, provider disagreement, nonce uncertainty, reorg or lost reply retains the original reservation and maximum liability. Do not automatically issue a new nonce, claim, signed intent or replacement. A definite safe revert still costs gas. Release only the proven unspent remainder after authoritative accounting. Returning an existing signed response must never trigger an implicit send.

A logical append-only journal inside the same DO is not rollback-proof. The pilot does not support journal restoration or automatic disaster recovery. Keep signing disabled after data loss, rollback or an uncertain journal epoch; do not serve from an old snapshot. The ordinary restart path must preserve the existing journal and exact signing requests/results. Any later restore design must reconcile an independently retained signer high-water/outbox with chain spends AND potentially signed, unbroadcast authorizations before reopening. Chain receipts alone are insufficient. Controlled restore drills remain deferred design cases, not a new main operator release gate.

Pausing stops new authorizations. It cannot revoke signatures already issued; outstanding liabilities remain reserved until definitively settled, expired or revoked under the actual protocol. No fake exactly-once claim: external effects use durable at-most-once authorization identity plus explicit uncertainty recovery.

Receipt accounting requires canonical block hash, safe confirmation, successful intended execution/event, actual payer debit and exact intent or original raw transaction. Recovery of consumed name/enrollment remains independent of current holder, authority freshness and discoverability. Current state is reported separately. Derived usage views/alerts may lag; they never authorize spend.

## Shared backend sender: manual nonce recovery proposal

A stuck lowest nonce can block every community using the backend sender. On detecting a stuck or uncertain original, pause new backend signing for that sender and bound the unsent queue. Keep reconciliation running. Do not keep assigning later nonces, switch sender, or use an alternate route automatically. This availability limitation is accepted for the small pilot.

A future qualified manual procedure may append a replacement attempt to the original operation. It must first verify the original signed raw bytes/hash, chain, sender, nonce, deployment, operation and outstanding reservation. Approval names the exact replacement payload digest, purpose, fee bound and expiry. An ordinary fee bump keeps the same sender/chain/nonce/to/data/value/access list and transaction type; only explicitly approved fee fields and, if independently simulated, gas limit may change. It cannot add authorization lists, delegation or other effects. An expired claim cannot be rescued by altering its signed claim or issuing new consent inside this procedure.

Cancellation is a separate explicitly approved purpose, not successful enrollment/claim consumption. An empty zero-value self-call is only a candidate for a separately verified plain EOA sender profile; it is not assumed safe for a delegated smart account. Preserve original raw/hash/nonce forever. Append each approved attempt's exact bytes/hash and its own authorization record before sending; never replace the original record or pass the replacement hash to an API that promises exact-original recovery.

Reserve each attempt's full upper-bound liability in the same community/global ledger before signing, conservatively retaining prior attempt reservations. If that temporary headroom is unavailable, refuse the attempt. The pilot does not optimize these into a shared maximum reservation. Manual approval cannot override ceilings. MOSS intent nonces, account execution and outer relayer nonces are separate protocols; this backend procedure does not qualify their replacement or cancellation.

Only proof of a canonical transaction from that sender with that exact nonce, included at or before a verified safe block, permits classifying the original as displaced on that canonical history. Verify the consuming transaction's bytes/hash, sender, chain and nonce, its receipt and block ancestry. A reverted consuming transaction still consumes its nonce. A pending/latest nonce increase, missing original receipt, receipt with matching enrollment but another sender/nonce, or elapsed time alone is insufficient. An account nonce query is supporting evidence, not the consuming-transaction proof. MegaETH's documented gateway may treat pending as latest; actual 6343 behavior remains unmeasured. [Nonce reference](https://docs.megaeth.com/developer-docs/rpc/reference/eth_gettransactioncount), retrieved 2026-11-14.

For a recorded approved replacement, prove its intended event/state independently and report replacement execution with its own hash, never original-hash success. Cancellation or an unrecognized consuming transaction is not operation success. An unrecognized transaction triggers a custody/accounting pause; release only liability demonstrably excluded, while retaining conservative coverage for any unaccounted debit. Reconcile the winning transaction's actual fee and release proven unspent reservations promptly. Unknown fee semantics retain an upper bound. If canonical evidence is later invalidated, reverse the settlement, restore liabilities and pause signing if budget headroom is insufficient. Safe is a confirmation rule, not a promise that reorgs are impossible.

This is a proposed attempt-aware recovery interface, not implemented SDK behavior. No automatic replacement, resend, new nonce, new grant or cross-route replay is introduced. Ordinary EVM nonce equality is specified in [EIP-1559](https://eips.ethereum.org/EIPS/eip-1559); provider replacement admission and smart-account behavior require separate qualification.

A contract claim deadline expiring does not expire an ordinary signed EOA transaction: it may still be mined and revert at Pirate's expense. An expired-unconsumed application result is therefore not authority to refund that transaction's fee reservation. MOSS expiry must likewise be shown to end the actual payer liability, not inferred from an intent field alone.
