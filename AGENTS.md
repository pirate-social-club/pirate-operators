## Testing behavior

Never write unit tests after you write code. Highly prefer E2E or integration
tests as the sole testing mechanism. Use them to verify complex features work.
At the end of those tests, produce a verifiable and repeatable artifact.

If you must test a system in isolation, first write down all the ways it could
fail, then write the code. Keep an isolated test only when it protects an
observable behavior, invariant or public contract against a credible regression
that existing E2E or integration tests do not catch.

A test that breaks under a behavior-preserving refactor is asserting
implementation, not behavior. Do not add it. Do not add assertion-free coverage
probes, source/import/string greps, mocks that implement the asserted behavior,
expected values generated by the code under test, tests that only keep a
test-only export or wrapper alive, or near-duplicates of a stronger test.
Artifact identity, cryptographic vectors and independent reproducibility checks
protect release contracts; do not confuse them with source-format assertions.

Never delete or weaken a failing test to make the suite pass. Fix the code, or
ask. Before deleting a test, read it and its production owner, identify the
retained behavioral coverage, and record any uncertainty.
